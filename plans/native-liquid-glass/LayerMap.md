# Liquid Glass layer map

Status: **approved A1 layer map; production conformance complete**

## Governing rule

Liquid Glass is a functional layer for navigation, controls, and transient
surfaces above content. It is not content decoration. Standard macOS components
receive the current system material automatically; jackin❯ does not recreate or
stack it.

This proposal requires:

- no explicit SwiftUI `glassEffect`;
- no `GlassEffectContainer` because no custom glass cluster exists;
- no `NSGlassEffectView` or `NSVisualEffectView` behind popover/window content;
- no custom blur, vibrancy, opacity, border, shadow, or corner radius used to
  imitate glass;
- no content row, table cell, quota row, metadata group, or progress control on
  a glass surface.

## Menu-bar surfaces

| Region | Layer | Material owner | Expected behavior | Prohibited |
|---|---|---|---|---|
| macOS menu bar | FUNCTIONAL | macOS | System adapts to desktop, tint setting, contrast, and active state | App-owned menu-bar backdrop |
| Provider status item | FUNCTIONAL | `NSStatusBarButton`/macOS | Native hover, press, focus, accessibility, and menu-bar appearance | Glass modifier, custom bezel |
| Status-item label content | CONTENT inside system control | jackin❯ data; system typography | Provider mark and Rust-owned values remain legible in native metrics | Chip/capsule background, decorative tint |
| Context menu | TRANSIENT FUNCTIONAL | `NSMenu`/macOS | System material, shadow, selection, keyboard navigation, inactive behavior | Custom menu surface or per-item glass |
| Popover host | TRANSIENT FUNCTIONAL | `NSPopover`/macOS | One system-owned popover material and shadow; responds to appearance/accessibility settings | Clearing host background, adding another material panel |
| Popover product identity | CONTENT | Generated template `Image` plus native `Text` | Centered noninteractive `jackin❯ desktop` identity; no independent surface | Branded glass, card, titlebar imitation, hit target |
| Popover identity/metadata/limits | CONTENT | No glass | Text, labels, native progress, and scrolling form one reading surface | Cards, nested panels, row glass |
| Popover account picker/buttons | FUNCTIONAL controls inside host | Native `Picker`/`Button` | Controls draw their own current system appearance | Explicit glass or colored capsule wrappers |

The popover is already the single transient functional surface. Its child
controls must not create a second translucent sheet. Regular-versus-clear custom
glass style is therefore not a design decision: no custom style is proposed.

## Usage window

| Region | Layer | Material owner | Expected behavior | Prohibited |
|---|---|---|---|---|
| Window and titlebar | FUNCTIONAL chrome | `NSWindow`/macOS | Internal `jackin❯ desktop` identity; standard key, main, inactive, and accessibility adaptation | Custom window shell, fixed corner radius, custom titlebar strip |
| Centered product title | CONTENT inside system toolbar | SwiftUI `.principal` `ToolbarItem` plus `Text` | Noninteractive `jackin❯ desktop`; native toolbar owns centering and adaptation | Logo button, decorative material, manual offset, destination title |
| Toolbar | FUNCTIONAL | Native toolbar generated by SwiftUI/AppKit | System grouping, overflow, scroll-edge adaptation, and one control treatment | Custom background, manual glass grouping, custom overflow |
| Sidebar toggle | FUNCTIONAL | Native SwiftUI toolbar `Button` bound to `NavigationSplitViewVisibility` | One fixed `.navigation` slot; Apple SF Symbol; system material, hover, focus, help, and accessibility | Duplicate automatic item, detail-group migration, hand-drawn icon, custom material, conditional relocation |
| Sidebar | FUNCTIONAL navigation | `NavigationSplitView`/`List` | System floating sidebar material, accent selection, collapse, inactive adaptation | Opaque custom background, rounded selection cards |
| Sidebar labels | CONTENT inside system navigation | Native `Label` | Provider identity only; no independent panel | Per-row glass or fixed selection tint |
| Sidebar product signature | CONTENT inside system navigation | Generated adaptive `Image` | Quiet, noninteractive canonical wordmark on transparent background | Toolbar logo button, brand card, independent material |
| Overview table | CONTENT | `Table` | Dense comparable records on the window content plane | Glass table, dashboard cards |
| Provider detail | CONTENT | `List`/`Form`/`Section` | One continuous data surface with native separators and insets | Card stack or ornamental material |
| Account picker | FUNCTIONAL control | Native `Picker` | Native pop-up/menu material when opened | Persistent glass account rail |
| Quota progress | CONTENT | Native `ProgressView` | Semantic value presentation; no backdrop sampling | Custom glass track, glow, chart |
| Context/picker menus | TRANSIENT FUNCTIONAL | macOS | Native menu material, focus, dismissal, contrast | Custom menu implementation |
| Sheet/alert if blocking | TRANSIENT FUNCTIONAL | Native sheet/alert | Used only for a truly blocking condition | Recoverable provider error in a modal glass card |
| Settings window controls | CONTENT plus native FUNCTIONAL controls | `Form`, `Picker`, `Toggle` | Standard settings appearance | Glass settings cards |

## Background extension and scroll-edge policy

- Default: do not add `backgroundExtensionEffect()` merely to make the window
  look glassier.
- If Phase 3 rendered evidence shows the native sidebar needs content extension,
  use the system effect once at the window content root, before overlays, and
  record why. It remains a functional-layer adjustment, not a content surface.
- Let native toolbar/sidebar scroll-edge behavior resolve automatically first.
- Use a hard scroll-edge style only if a tested pinned header or free-floating
  title loses legibility. Never reproduce the edge with a gradient mask.
- The Overview table and provider detail scroll beneath native chrome only when
  their native container establishes that relationship.

## Control tint policy

- No custom glass tint is proposed.
- System accent color owns sidebar selection and standard control emphasis.
- A prominent tint is permitted only if a later selected structure identifies
  one genuine primary action in a bar. Refresh and Open Usage are utility
  actions, so neither is promoted by default.
- Provider brand color may appear in an existing content identity mark only when
  that asset already uses color and remains legible.
- Adaptive jackin❯ phosphor may tint healthy native quota progress tracks. This
  is semantic content color, not glass or control-background tint. Warning and
  danger stay system orange/red, with text carrying every state.
- Product/provider color must not tint glass, toolbar actions, popover actions,
  or selections.

## State adaptation

| Environment | Native expectation | Design consequence |
|---|---|---|
| Light appearance | System materials and semantic colors adapt | No fixed translucent fill or border |
| Dark appearance | Same hierarchy with system adaptation | No dark-mode-specific fake glass |
| Inactive/non-key window | Window glass and selection recede | No bright child panel may remain visually active |
| Reduce Transparency | System components substitute their supported treatment | No custom translucent region requiring a manual fallback |
| Increase Contrast | System controls/separators strengthen | Text and state remain meaningful without subtle material edges |
| Reduce Motion | System transitions adapt; custom motion absent | Refresh progress remains functional, not decorative |
| Liquid Glass clear/tinted preference | System-owned material changes | No custom surface that cannot follow the preference |

## Overlap and nesting audit

The recommended structure has one system popover surface and one system window
chrome/navigation layer. Native controls may appear inside them, but there is no
explicit glass-on-glass nesting and no overlapping custom glass. The correct
render-pass budget is therefore system-owned; jackin❯ does not invent a numeric
glass budget.

## Layer acceptance condition

Rendered evidence must show that removing all current custom material helpers
does not reduce hierarchy. If hierarchy depends on restoring a decorative
content panel, the structure has failed and returns to the design gate rather
than adding custom glass.
